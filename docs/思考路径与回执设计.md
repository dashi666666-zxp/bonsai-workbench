# 思考路径（PSV）与强制回执 —— 设计说明（v0.4.0）

本文记录 bonsai-workbench v0.4.0 的两项内置能力：**内化一条思考路径**、**每次 run 结束强制生成回执报告**。目标不是把提示词写得更长，而是把「先想再做、做完自检」「结束必留凭证」变成代码推进的阶段与产物。

---

## 1. 要解决的问题

1. 27B 本地模型直接作答时，容易「上来就写」：不先确认任务口径、不先看已检索到的资料，长任务里到处试工具。
2. 答案没有固定结构，用户无法快速判断「结论是什么、依据在哪、哪些没验证」。
3. run 记录散在事件流里：结束之后要翻 `runs/*.jsonl` 才知道做了什么、调了多少工具、引用了哪些资料。
4. 失败与中断恰恰最需要凭证，但旧实现只有插件钩子（`receipt-writer`），插件被删/被关/自己报错就没有回执。

## 3. 路径与代码落点

阶段顺序由 `model/agent.mjs` 的 `runAgent` 推进，模型只负责每一阶段的输出：

| 阶段 | 由谁推进 | 产物 | 失败兜底 |
| --- | --- | --- | --- |
| 计划 | 代码：RAG 检索之后、进入主循环之前发一次规划请求 | `plan = {steps[], source:'llm'\|'fallback'}`；注入 system prompt 的【本轮计划】 | 请求失败/超时/解析为空 ⇒ `fallbackPlan()` 确定性 3 步 |
| 取证 | 代码：已有 RAG 自动检索 | `【知识库检索资料】` + `[S#]` 出处 | 检索失败 emit `rag_miss`，计划仍执行 |
| 作答 | 模型主循环（工具调用照旧） | 答复文本 / 工具轨迹 | 步数用尽 ⇒ `status:'error'` |
| 自检 | 代码：无 tool_calls 分支收尾时 | `thinking_verify {ok,hasConclusion,hasBasis,hasSelfCheck,missing}` | `requireSelfCheck=true` 且缺段 ⇒ 重写一次 |

## 4. 计划阶段

- 请求：`chatStream({ messages: [system 规划器, user planRequest({task, sources})], max_tokens: planMaxTokens(180), options:{temperature:0.2}, think:false })`，超时 `planTimeoutMs`（默认 30s），用 `AbortSignal.any([signal, AbortSignal.timeout(...)])` 与用户「停止」联动。
- `planRequest()` 只要求「2–5 步编号列表」，并把已命中的资料出处作为上下文（`[S1] a.md · 标题 行 1-9`），避免规划脱离资料。
- 解析：`parsePlan(text, maxPlanSteps)` 认 `-`/`*`/`+`/`1.`/`1)`/`1、` 前缀，去掉 `**`，单步 >120 字截断，最多 `maxPlanSteps`（默认 5，夹在 2–8）。
- 兜底：`fallbackPlan({rag})` —— 有资料「读资料 → 标 [S#] 作答 → 自检」；无资料「确认目标 → 工具取证 → 作答自检」。**兜底也保证阶段存在**，回执里能看出 source 是 `llm` 还是 `fallback`。
- 关闭：`thinking.enabled=false` 完全不注入、不发规划请求；`thinking.planCall=false` 保留思考路径规则但跳过规划请求（用兜底计划）。

## 5. 注入格式

```
【思考路径 · 计划→取证→作答→自检（PSV）】
1. 先按【本轮计划】推进；计划不周可以调整，但每步要有结果。
2. 取证优先用已检索到的资料；需要新证据再调工具，并记录来源。
3. 作答先给结论，再给依据；知识库内容必须标 [S#]。
4. 收尾自检：结论是否有依据、哪些没验证、下一步做什么；资料不足直接说。

【本轮计划】
1) 读【知识库检索资料】，确定哪些 [S#] 能回答任务
2) 依据资料作答，每个结论标注 [S#]；资料不足就明说
3) 自检引用编号与边界，未验证项写清
```

## 6. 自检

`checkAnswerPath(answer, {requireSelfCheck})` 只判结构：

| 判据 | 正则/依据 |
| --- | --- |
| `hasConclusion` | `结论：` / `## 结论` |
| `hasBasis` | `[S1]` 形式引用 / `依据：` / `根据` / `资料来源` / `引用` |
| `hasSelfCheck` | `自检：` |

- 默认 `requireSelfCheck:false`：只 emit 事件写回执，不打断模型。
- `requireSelfCheck:true`：缺段时追加一条「【系统校验】最终答复缺少：…。请按『结论 / 依据 / 自检：…』重写」的 user 消息，重写一次（`verifyRetries<1` 护栏）。
- 这是**软判据**：它检查「有没有这三段」，不检查「内容对不对」——内容真伪仍由引用校验（形式）与人工判断负责。

## 7. 强制回执

### 7.1 触发点（为什么「必须」）

`controller/runs.mjs`：

```
executeRun(run):
  try { await runLoop(run) }                       // 正常：done / stopped / error
  catch (e) { 置 error、saveSession、durable、emit run_end }
  await finishReceipt(run)                          // 任何结局都走这里
  finally { scheduleCleanup(run) }
```

- `runLoop` 末尾（插件钩子之后）也调 `finishReceipt`，覆盖正常路径。
- `finishReceipt` 幂等：`run.receipt` 已存在直接跳过；`receipt.enabled=false` 跳过。
- 自身异常：写最小 md（runId / 状态 / 错误），emit `receipt` 带 error。
- 停机补齐：`initRuns()` 对上次遗留 `status:'running'` 的记录调 `writeInterruptedReceipts()`，补写「⚠ 已中断」（已有 md 跳过）。
- 写盘：`<BW_RECEIPT_DIR>/<runId>.md|json`，tmp + rename；runId 不在白名单时落成 `run-<base36>`。

### 7.2 格式（对齐全项目「结论先行」口径）

```markdown
# 回执报告 · r_xxx

**结论**：✅ 完成 — 用一句话说明…

| 项 | 值 |
| --- | --- |
| 运行 ID | … |
| 会话 | … |
| 状态 | done |
| 任务 | … |
| 模型 / 权限 | llama/bonsai-2-27b · full-access |
| 时间 | 开始 · 结束 · 用时 · 首字 · 首答 |
| 性能 | prompt eval / decode tps |
| 步数 / 工具 | N 步 / M 次 |
| Token | prompt ⇒ eval |

## 结论
## 做了什么        （表：# / 阶段 / 动作 / 详情 / 结果：计划行、检索行、每个工具一行、自检行）
## 验收证据        （表：检查项 / 结果 / 判定：计划、RAG、引用校验、自检、动作统计、回执落盘）
## 触及文件
## 边界与未验证
## 下一步
---
由 bonsai-workbench v0.4.0 内置回执生成…
```

`<runId>.json` 是同一份内容的结构化版本，含 `status/plan/toolCalls/files/usage/rag/ragVerify/thinkingVerify/receipt{version,md,json}`。

### 7.3 与插件的关系

- 内置回执在 `runEnd` 插件钩子**之后**写：同路径会覆盖插件版本，内置格式为权威。
- `examples/plugins/receipt-writer/` 保留（可作为「如何写 runEnd 钩子」的示例），但不再是回执的必要条件。

## 8. 事件与 UI

| 事件 | 主要字段 | UI 呈现 |
| --- | --- | --- |
| `thinking_stage` | `{stage:'plan',status:'start'}` | 运行状态行「思考路径 · 制定计划」 |
| `thinking_plan` | `{steps[],source,ms}` | 系统提示行「思考路径 · 计划（模型 · 812ms）」+ 编号步骤 |
| `thinking_verify` | `{ok,hasConclusion,hasBasis,hasSelfCheck,missing[]}` | 「自检通过」/「自检提示：缺 结论段」 |
| `receipt` | `{runId,md,json,bytes,statusText}` | 「回执已生成（5,231 B）」+ md 路径 |

系统提示行按 `sessionId` 缓存最近 40 条（`state.notices`），`run_end` 触发重渲染后仍可见。

## 9. 参数

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `thinking.enabled` | true | 关闭后不注入、不规划 |
| `thinking.planCall` | true | 是否发规划请求（false 用兜底计划） |
| `thinking.maxPlanSteps` | 5 | 2–8 |
| `thinking.planMaxTokens` | 180 | 规划输出上限（64–400） |
| `thinking.planTimeoutMs` | 30000 | 规划请求超时（3000–120000） |
| `thinking.requireSelfCheck` | false | 缺段是否重写一次 |
| `receipt.enabled` | true | 是否写内置回执 |

`run` 级覆盖：`POST /api/runs {overrides:{thinking:{...}, receipt:{...}}}`（`mergeRunCfg` 对 `thinking/receipt/rag/ctx` 做对象浅合并）。

## 10. 验收与复跑

```bash
node test/smoke.mjs                      # 离线：156 项（含思考路径 / 回执 29 项）
node _scratch/live_v040_probe.mjs        # 真机 4790：正常 / 失败 / 中断三种结局都出回执
```

- 离线断言覆盖：`THINKING_PATH` 四阶段、默认开启、思考块内容、关闭为空、`parsePlan` 解析与上限、`planRequest` 带出处、`fallbackPlan` 两种、`checkAnswerPath` 三态；回执合成事件 → md 五段与结论状态、json status/plan/toolCalls、落盘、非法 runId 拒绝。
- 真机探针验证：`runA`（done）有 `thinking_plan`（≥2 步）与回执；`runB`（`maxSteps:1` 必出错）仍有回执且结论为「❌ 出错」；`runC`（起跑后 stop）仍有回执且结论为「⏹ 已停止」。实测 `LIVE_V040_PROBE PASS 54 / 0`。
- 界面侧：`UI_V040_PROBE PASS 24 / 0`（计划 / 自检 / 回执三类 sysline 在 `run_end` 重渲染后仍在；右栏 `.md` 预览出「# 回执报告」与结论）。
- 崩溃补齐：`INTERRUPTED_RECEIPT_PROBE PASS 11 / 0`（`markInterrupted()` + `writeInterruptedReceipts()` 给 status=running 的落盘 run 补写回执，结论「⚠ 已中断 — 进程重启…」，已写过不重复补）。
- 结果数字见 `README.md` §7。

## 11. 边界

1. **规划不是免费**：每次 run 多一次 LLM 小请求（≤180 token，实测 1–3s）；`planCall=false` 可省。
2. **自检是结构判据**，不判真伪；`requireSelfCheck` 只保证「重写一次」，不保证重写后合格。
3. **回执是事件快照**：模型自述内容原样摘录，工具结果只记 ok/首行；「验收证据」不等于外部事实已验证。
4. **硬杀进程当轮无法补写**：回执在下次启动由 `initRuns` 补成「已中断」。
5. **计划可能过时**：中途 steer 或工具结果改变方向时，计划段仍在 system prompt 里；模型被规则允许调整计划，但注入文本不会自动重写。
6. 尚未做：多路径推理（ToT/Reflexion）、把计划做成独立可编辑状态、回执 PDF/HTML 导出。
