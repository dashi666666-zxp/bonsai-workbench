# 生成速度调优（本机实测，2026-11-08）

> 目的：把「怎么让每秒 token 数变高」这件事一次测清、写死结论，避免以后再靠启动参数碰运气。
> 复跑：`npm run bench`（对已运行的 llama-server 打，不启停服务）。

## 结论先行

1. **decode 就是 33–41 tok/s**（首轮、同批连跑），由「8 GB 笔记本卡 + 5.95 GB 权重」的显存带宽决定，**任何启动参数都改不了这个上限**。
2. **投机解码（ngram 系）首轮 0 收益**：4 组真实 agent 提示的 `draft_n` 全是 0，tg 变化在 ±2% 内、输出逐字一致。它只在「重复已生成过的文本」时爆发（同一 prompt 连打第 2/3 次）——那是基准假象，不是能力。
3. 其余候选参数全部无效或有害（`-ub 1024` 掉 46%、`--prio` 只 +1%、`-ctk/-ctv q4_0` 只 +2.6% 且有质量风险）。
4. 真正的提速杠杆不在启动参数，在**少生成 token**（思考开关、计划调用）和**少往返**（工具并发、减少重发）。

| 项 | 值 |

## 为什么是带宽限制

- 生成期间 `nvidia-smi` 采样：SM 时钟 2790–2805 MHz（上限 3090，约 90%）、温度 62–69 °C、功耗约 97 W、GPU util 98–99% ⇒ **没有热降频，没有算力闲置**。
- 每个 token 要把 5.95 GB 权重读一遍：`5.95 GB / 25.7 ms ≈ 231 GB/s`；按该卡通道上限约 340 GB/s 折算，理论上限约 57 tok/s，实测用掉约 68%。
- 推论：想让 decode 变快只能减小权重体积（更激进的量化）或换卡，调参无用。

## 试过什么

基准：4 个 agent 风格提示（tool/summary/code/rewrite），每项首轮，逐字比对输出。

| 手段 | 首轮 tg 变化 | 结论 |
| --- | --- | --- |
| `--spec-type ngram-mod` | −1.7% ~ +0.3%，drafts=0 | 首轮无用（见下节） |
| `--spec-type ngram-simple` | 首轮同上 | 同上 |
| `-ub 1024` | **−46%** | 有害（显存压力） |
| `-b 4096 -ub 2048` | 混杂（含 −45%） | 不可用 |
| `-ub 256` / `-b 2048 -ub 512` | 0%（prefill 也不变：595–605 tok/s） | 无收益 |
| `--prio 2 --prio-batch 3` | +1% | 噪声级，可留可去 |
| `--cache-reuse 256` | 0% | 无收益 |
| `GGML_CUDA_FORCE_MMQ=1` | 0% | 无收益 |
| `GGML_CUDA_USE_GRAPHS=0` | 0% | 无收益 |
| `-ctk q4_0 -ctv q4_0` | +2.6%（显存降到 6785 MiB） | 收益小、需 mean-centering、有质量风险，不采用 |

prefill 真值（4514 token 长提示）：**约 600 tok/s**，即 4500 token 的提示约 7.5 s；`-ub`、`-b`、`--prio` 对它没有影响。短提示看到的「78 tok/s」是固定开销被摊薄的结果，不是 prefill 慢。

## 投机解码：数字为什么会骗人

同一份 `tune_verify.mjs` 先给出 `+52%`（quote）、`+217%`（chat）、`+689%`（code），差点被当成重大突破。拆开看：

- 那些用例**连打了同一 prompt 三次**；第 2/3 次时上一轮自己生成的文本已经在 ngram 缓存里，投机解码命中自己 ⇒ 数字虚高。
- 换成「每项只取首轮」的 `ab_spec.mjs` 后：tool 50.0→49.5、summary 47.6→46.8、code 48.5→48.2、rewrite 48.0→48.2，`draft_n = 0`，输出逐字一致 ⇒ **真收益 0**。
- `npm run bench` 已把这条教训写进工具：分别报 `tg1`（首轮）与 `tg2/tg3`（重复轮），重复轮高出 20% 就打印「=缓存命中，非参数收益」。

结论：`--spec-type` 只在**重复/复述型**负载（长文档改写、结构化重复、把上文再吐一遍）有收益。本工作台的主负载是首次生成，故**默认不开**；需要时手改 `bonsai.config.json` 的 `llamacpp.extraArgs` 追加 `--spec-type ngram-mod`，并用 `npm run bench` 自测。

## 已内化的改动（0.5.1）

1. **默认参数回归干净值**：`-ngl 99 -fa on -c 16384 -ctk q8_0 -ctv q8_0 --jinja -np 1`，不带 `--spec-type`；smoke 加了「不默认开投机解码」的回归断言。
2. **修配置 bug**：`ctx.summaryChars` 原为 `1e+104`（`Infinity` 被 JSON 序列化后的产物），被 `compress.mjs` 的 `clamp(…, 200, 4000)` 夹到 4000 ⇒ 摘要比默认 1200 长 3.3 倍、白烧 token。已改回 `1200`，smoke 加区间断言。
3. **新增基准工具** `test/bench.mjs`（`npm run bench`）：4 个固定提示 × N 轮，报 pp/tg/drafts 并自动标注缓存假象。以后任何参数改动都先跑它，同批连跑才算数。
4. **记录本页**：结论、数据与「不要试」清单落盘，避免重复踩。

## 不属启动参数、但真能提速的（下一步候选）

- **思考开关**：`think: true` 时每个回答多生成几百个思考 token（39 tok/s 下就是十几秒）。简单任务关掉收益最大。
- **计划调用 gate**（`model/agent.mjs` 每轮固定多一次 4.5–5.2 s 的模型调用）：闲聊/单步任务跳过计划。
- **减少往返**：`/api/state` 拆快慢包（现 54 ms/次，每次 run_end 都拉）、read 类工具并发、前端增量渲染。

## 上下文加高（0.6.0）

目标：`-c` 从 16384 提到尽量大，不动 KV 量化（q8_0 保持零质量损失）。做法＝每个候选值起一台临时 `llama-server`（8083 端口、与生产同参数），等 `/health`、读 `/props` 的 `n_ctx`、量 nvidia-smi 显存、再跑 4 提示 bench 判「是否已被迫走 WDDM 分页」，最后杀掉。

| `-c` | 加载 | 显存 (MiB) | 首轮平均 decode | 判读 |
| --- | --- | --- | --- | --- |
| 16384（原值） | ok | 7674 | 37–45 | 生产基线 |
| **32768** | ok | **7685** | **37.6** | **可用（定稿）** |
| 36864 | ok | 7558 | 21.0 | 已部分分页 |
| 40960 | ok | 7571 | 9.0 | 明显分页 |
| 49152 | ok | 7600 | ~2.5 | 严重分页 |
| 65536 | ok | 7600 | ~2.2 | 严重分页 |

关键教训：**「能加载」不等于「可用」**——49152/65536 都返回 `status ok`、`n_ctx` 正确、显存读数还更低（WDDM 把放不下的页换到共享内存，nvidia-smi 反而不涨），但 decode 从 37.6 掉到 2.5。判据必须是「同批 bench 没有掉速」，只看加载成功会得出「65536 也能跑」的错误结论。

32768 的额外验证（`_scratch/ctx_verify.mjs`，真实长提示）：12,000 字符 → prompt 6,020 token / 623 tok/s / 9.7 s 回「收到」；40,000 字符 → **prompt 20,021 token** / 560 tok/s / 35.8 s 一次跑通（这已超过原 16384 上限，证明新上下文真能用）。

副产物：`_scratch/ctx_probe.mjs`（起停临时 server + 加载/显存/bench 一条龙，`--ctx/--ctk/--ctv/--tag`）与 `_scratch/ctx_verify.mjs`（真实长提示验证），日志落在 `_scratch/ctx_<tag>.log`。注意临时 server 与生产同卡，跑之前必须先停生产实例，跑完再拉起工作台。
